## Phase 0 outcome

Finished 14 November 2026 on `Dev-2`. The gate holds on both backends: the same image as before the
restructure, validation output empty apart from one third-party message, frame time on screen.

- **Layers.** Six projects: `RHI`, `Renderer` (new DLL), `Engine`, `Game`, `Editor`, `Standalone`.
  Shared settings in `Solution/Build/Common.props`; project files generated by
  `Tools/GenerateProjects.py`. Release builds the libraries as DLLs, as Debug does.
- **Moved out of RHI.** `Renderer`, `Material`, `ImageImport` and the HLSL now live in
  `Solution/Renderer`. Shaders compile as a build step of that project into a gitignored folder.
- **Repository.** The NoesisGUI SDK is out of the tree (`NOESIS_SDK` or a default path), its DLLs and
  assimp's are copied by the build, the absolute path is gone, and README.md has the build steps.
- **Handles.** `Handle<Tag>` and `HandlePool` give generation-checked `BufferHandle`, `ImageHandle`
  and `DescriptorSetHandle`. Destroyed resources are released `FramesInFlight` frames later.
- **External passes.** The executor no longer calls Noesis. `Renderer::EnlistExternalPass` runs
  `Prepare` before the frame and `Render` inside a generic overlay pass on the back buffer with a
  cleared stencil. Noesis and Dear ImGui both attach this way.
- **Debug overlay.** Dear ImGui is built once into `Engine.dll`. `DebugOverlay` shows backend,
  frame time and draw calls, and later phases add panels with `EnlistPanel`. The Editor now runs on
  Vulkan as well.
- **Switches.** `-dx12` and `-vulkan` choose the backend; the Editor also takes `-play`.
- **Defects.** 1, 3, 4, 6, 7 and 8 fixed. 2 fixed by copying push constants into the draw. 5 (one
  mapped copy shared by every frame in flight) is fixed in Phase 1 by the ring allocator.
- **Mesh rendering** works again. `MeshAsset::Serialize` was wiping the vertex cache before upload,
  and skinned meshes uploaded with the static vertex stride.

Open items carried forward:

- **D3D12 multiview** (closed in Phase 2, shadows render one layer per pass). Direct3D 12 has no view instancing set up, so the multiview shadow pass fills
  only layer 0 there (`SV_ViewID` is 0). Only one light is used today, so the image matches. Either
  add `D3D12_VIEW_INSTANCING_DESC` or render one view per layer when more lights cast shadows.
- **Noesis debug message.** On Direct3D 12 the debug layer reports that one of Noesis's own offscreen
  render targets "must be initialized with a Discard/Clear/Copy" operation. It goes away when Noesis
  is not started, so it is treated as third-party.
- **Skinned mesh on D3D12.** The "Derp" mesh looked different on D3D12 than on Vulkan in the Editor
  and was missing from one Standalone capture. Settled in Phase 1: the hand animation moves it a long
  way, so captures differed by timing; frozen, both backends match.
- Runtime paths are relative to the project directory.
- `ImageAsset` and `MaterialAsset` are still stubs from the unfinished asset work.

## Phase 1 outcome

Finished 14 November 2026 on `Dev-2`. The gate holds on both backends with validation clean: the
`-stress` scene draws 10,014 objects in 14 instanced batches per pass (29 draw calls in all), and
the standard passes are built only on the public pass graph API.

Steps 1 to 3 of the order of work landed as one change, with the slim G-buffer. Doing them in
sequence would have meant porting the variant and attachment code onto the ring first, only to
delete it in the next step.

**RHI**

- `PipelineLayout` is its own object (a root signature or `VkPipelineLayout`). Pipelines either share
  one or build their own. Set 0 stays reserved for the two global samplers.
- `Pipeline` holds pipeline state only. Owned attachments, `IOResource`, `InputPipelineIDs` and the
  variant machinery (`IsVariant`, `VariantResourceLayout`, `VARIANT_DESCRIPTOR_SET_BASE`,
  `PipelineVariants`) are gone.
- Frame ring in `BufferAllocator`: one host-visible buffer, 16 MB per frame in flight,
  bump-allocated with any alignment, reset when the frame slot begins. Fixes defect 5.
- Dynamic uniform buffers take their offset at bind time: `UNIFORM_BUFFER_DYNAMIC` on Vulkan, root
  CBVs on D3D12. Storage buffers are written on Vulkan and are structured-buffer SRVs on D3D12. The
  scene set binds the whole ring once and shaders index it by absolute element.
- On D3D12 each set is at most one descriptor table plus one root CBV per dynamic uniform buffer.
  Every D3D12 heap (shader-visible, RTV, DSV) uses a range free list.
- `CreateImage` without initial data creates attachments that can also be sampled, with array
  layers and an optimized clear value. Sampled D3D12 depth is typeless with `D32_FLOAT` and
  `R32_FLOAT` views. Added `R16G16_UNORM`, `R32_FLOAT` and `B8G8R8A8_UNORM`.
- The executor takes `ImageHandle`s everywhere, including the swapchain image (`GetBackBuffer`).
  Barriers are layout to layout; stages and access masks are derived by the backend.
- Draws take an instance count. The first instance goes in a 16-byte push constant and draws always
  start at instance 0, because `SV_InstanceID` differs between the backends.
- `Uploader` is deleted.

**Renderer**

- `PassGraph`: retained passes and images. Passes declare colour and depth writes with load ops and
  sampled reads. The graph sorts them topologically (ties keep declaration order; overlay passes run
  after every raster pass), creates and resizes images, places barriers from tracked layouts, and
  allocates and rewrites each pass's input descriptor set. The back buffer starts each frame
  `Undefined` and ends `Present`, and is cleared if nothing wrote it before the first overlay pass.
  `EnlistExternalPass` adds an overlay pass.
- `Passes/DeferredPasses`: shadow, G-buffer and lighting, using only the public API. The lighting
  pass is added first on purpose, so the sort is what puts it last.
- `MeshRegistry` and `MaterialRegistry` with `MeshHandle` and `MaterialHandle`. Meshes store vertex
  layout and a bounding sphere; materials are shared by name and reference counted.
- `RenderScene` snapshot (objects, bone matrices, lights, camera), filled once per frame by
  `SceneExtraction` in the engine.
- `DrawList` per view: frustum-cull bounding spheres, sort by a 64-bit key (vertex layout, material,
  mesh, object), merge equal neighbours into instanced draws, write instance data (world, normal
  matrix, bone offset) to the ring in sorted order. The shadow and G-buffer passes each build one.
- Bones live in the ring as a storage buffer, so the skinned pipelines share the scene layout.
- Slim G-buffer: albedo `R8G8B8A8_UNORM`, octahedral normal `R16G16_UNORM`, material
  `R8G8B8A8_UNORM`, sampled `D32_FLOAT` depth. The lighting pass rebuilds world position from depth
  and the inverse view-projection. 16 bytes per pixel, about 59 MB at 2560 x 1440.
- `DebugOverlay` gets a "Renderer" panel with object count, and instances, batches and draws per pass.

**Engine**

- `TempGameObject` and `EngineConstants.h` are deleted. `MeshComponent` carries a material per
  submesh and, for skinned meshes, a bone palette that `DerpMover` writes.
- `SceneNode` world matrices are `Local * ParentWorld` (row vectors), and the importer stores true
  local matrices, so imported hierarchies keep the transforms they had.
- `Camera` unsubscribes from the resize event, and the constructor that takes a matrix no longer
  zeroes its near and far planes.
- Switches: `-stress` adds the 10,000 object grid; `-freeze-animation` holds the Derp still so
  captures from the two backends can be compared.

**Checked**

- Debug: Standalone and Editor `-play` on both backends, with and without `-stress`; window resize on
  both; the Editor with no game running. Stderr is empty apart from the known Noesis message on D3D12.
- With the animation frozen, Vulkan and D3D12 frames differ by a mean of 0.55 out of 255, which is
  the overlay text. The shells match the Phase 0 image.
- The skinned Derp now matches across backends, which settles the Phase 0 open item. It moves a long
  way because `DerpMover` translates bones by 0.1 in bone space under an armature scaled by 100; that
  is the hand animation, replaced in Phase 3.
- Release, `-stress`, last frame: about 32 ms on D3D12 and 55 ms on Vulkan. The shells are high
  poly, and on Vulkan the shadow pass renders all four multiview layers, three of them for lights that
  do not exist, while D3D12 renders one. Not optimized yet.

**Corrections after review** (commit "Phase 1 corrections", from `Docs/Handoff-Phase2.md`):

- Uploads go through an upload context per backend: its own command list or buffer and a fence that
  only counts up. The per-frame D3D12 transfer list is gone, so an upload is safe at any time.
  Before this, D3D12 buffer and image uploads signalled one fence with two schemes and could skip
  the wait.
- One sampler table (`GlobalSamplers`) builds the D3D12 static samplers, now visible to every stage,
  and the Vulkan set 0: `s0` linear repeat 16x anisotropic, `s1` point clamp, `s2` linear clamp, `s3`
  point repeat. Vulkan sampled images are `SAMPLED_IMAGE`; `DescriptorBinding::Sampler` is gone.
- Memory access has named presets (`DeviceLocalMemory`, `UploadMemory`, `ReadbackMemory`). A
  CPU-readable buffer is a readback heap on D3D12.
- Vulkan descriptor pools chain when full; a set remembers its pool.
- Vulkan recreates the swapchain when it is out of date or suboptimal and skips that frame.
- `-novsync`; vsync is on by default on both backends (Vulkan used to pick mailbox, uncapped).
- `VK_EXT_descriptor_buffer` is no longer required.
- Frozen captures vary between two states from run to run on both backends, probably a UI animation
  phase. Compare runs in the same state: Vulkan and D3D12 then differ by a mean of 0.39 out of 255.

The Release frame times above are not comparable: D3D12 was vsync-capped and Vulkan was not.
Phase 2 re-measured them.

Open items: carried into "Phase 2 outcome". The D3D12 view-instancing gap is closed there.

## Phase 2 outcome

Finished 14 November 2026 on `Dev-2`, following `Docs/Handoff-Phase2.md`, steps 1 to 9 including the
optional step 9. The gate holds on both backends with validation clean: with `-compute-test` a
compute pass writes a 256 x 256 image from the frame number, a raster pass draws it into a corner of
the back buffer, and a row read back each frame matches the same function on the CPU. Latency is
measured, not fixed: 1 to 3 frames, never waiting.

**RHI**

- Formats `R8_UNORM`, `R16_UNORM`, `R16_FLOAT`, `R16G16_FLOAT`, `R16_UINT`, `R32_UINT`. `CreateImage`
  checks the format supports each requested use and throws a clear error if not.
- `BufferUsage` is flags (vertex, index, uniform, storage, transfer); `BufferType` is gone.
- Subresource ranges (base mip, mip count, base layer, layer count; zero counts mean all) on
  descriptor bindings, attachments and transitions. Vulkan caches a view per range on the image;
  D3D12 writes SRVs and UAVs with the range and claims RTV and DSV slots per range, released with
  the image. Array images always get array views, so shaders declare `Texture2DArray` for them.
- `ImageLayout::Storage` (`GENERAL` / `UNORDERED_ACCESS`); a Storage to Storage transition is a UAV
  or memory barrier. Compute is in the `ShaderReadOnly` stage mask.
- `DescriptorType::ReadWriteStorageBuffer` (structured UAV on D3D12) and `TransitionBuffers`.
- `CopyBufferToImage` and `CopyImageToBuffer` by mip, layer and rectangle, with `CopyRowPitch` for
  the 256-byte D3D12 row pitch and `CopyPlacementAlignment` for buffer offsets.
- Compute pipelines (`Pipeline::CreateCompute`), compute bind points, `Dispatch`.
- `GetCompletedFrameNumber` without blocking. On Vulkan the frame of the slot being reused is
  remembered when its fence wait succeeds, because the fence is reset straight after; without that
  the query could stall for hundreds of frames.
- Timestamp queries, one set per frame slot, read when the slot begins again (results are a few
  frames old). Passes and their GPU milliseconds show in the Renderer panel and the shutdown printout.
- One render-finished semaphore per swapchain image instead of per frame slot. With vsync on, the
  validation layer reported a semaphore still in use by the swapchain.
- `ViewMask` is gone from `PipelineDesc`, `RenderingDesc` and `PassDesc`.

**Renderer**

- Pass graph: `PassKind::Compute`; `StorageWrites` beside `SampledReads`, ordered like colour
  writes; `GraphImageDesc::MipLevels` and `IsStorage`; `ImportImage` for images the graph does not
  own; `Order` breaks ties for every kind of pass; a GPU timer around each pass. Buffers stay out of
  the graph; Phase 3's compute skinning will shape their declarations.
- `Readback`: `Watch` an image once, then `Request` a region; copies run in one compute pass placed
  after every other non-overlay pass, and callbacks fire at the start of the frame in which the GPU
  is seen to have finished. `Watch` is an addition to the handoff's API: the pass declares watched
  images as reads, and adding one in the middle of a frame would change the graph while it runs.
- `MipGenerator`: material textures are created with a full mip chain and storage usage, the upload
  fills mip 0, and an early compute pass (`Order` lowest) fills the rest with a 2 x 2 box filter, four
  textures a frame. The previous mip is read through an SRV, the next written through a UAV.
- Shadows: one raster pass per shadow-map layer, each with its own culled draw list and the light
  index in the draw constants. This closes the D3D12 view-instancing gap and removes the three
  wasted multiview views on Vulkan.
- `ComputeTestPass` (`-compute-test`), the gate test, uses only the public graph and readback API.

**Checked**

- Debug: Standalone Vulkan and D3D12, Editor `-play` on both, `-stress` and `-compute-test` on both,
  `-novsync` and window resize on both. Every run exits 0; stderr holds only "DirectX debugging
  enabled." and the known Noesis message.
- Gate: Vulkan "1007 readbacks matched, latency 2 to 3 frames" with vsync; D3D12 "852 readbacks
  matched, latency 1 to 3 frames". Release `-compute-test`: 909 readbacks matched, latency 1 to 3 frames (Vulkan).
- 9 mip chains generated (3 materials x 3 textures). Frozen frames of Vulkan and D3D12 in the same
  run state differ by a mean of 0.23 out of 255; step 9 left the image unchanged (0.57 / 0.58
  against step 8).
- Release `-stress -novsync`, last frame: Vulkan 31 to 33 ms (GPU: G-buffer 16.9 to 17.6, shadow 13.9); D3D12 30 to 32 ms (GPU: G-buffer 16.4, shadow 13.8). Both are GPU-bound on the high-poly shells. Before step 9 Vulkan was 54 ms
  (shadow 36 GPU ms against D3D12's 14). These replace the Phase 1 numbers, which mixed a
  vsync-capped D3D12 with an uncapped Vulkan.

Open items:

- The material set is a convention: set 2 of `Renderer::GetSceneLayout()`. Phase 4 replaces this.
- Shadow passes for missing lights still clear their layer (about 2 microseconds each).
- `UpdateDescriptorSet` rewrites in place and is only safe after `WaitForGpu`, which resize does. New
  code allocates a new set and frees the old one instead.
- Frozen captures vary between two states from run to run, probably a UI animation phase; compare
  runs in the same state.

Carried, not part of Phase 2:

- Colour space: textures and the back buffer are `UNORM`, the lighting shader clamps and there is no
  tone mapping, so mips are filtered on stored values. sRGB formats cannot be storage targets without
  typeless or mutable formats. Phase 4 decides.
- Every buffer and image is its own device allocation.
- The lighting pass squeezes the full-window G-buffer into the Editor's game viewport.
- `RHIStructures.h` exposes `d3d12.h` and Vulkan types to every layer.
- `D3DPipelineExecutor::GetBackBuffer` uses its own frame counter, not `GetCurrentBackBufferIndex`.

## Phase 3 outcome

Finished on `Dev-2` on 16 November 2026, following `Docs/Handoff-Phase3.md`. Step 1 is the "Phase 2
corrections" commit, steps 2 to 5 and 7 are "Phase 3", and step 6 is "Phase 3: the character".

**The character.** A Genesis 9 figure in `TempAssets/CharBlend.blend` and `.fbx`: 143 bones under a
`Genesis9` armature, 7 skinned meshes and 427,610 vertices (402,600 in the body), no shape keys and
no actions. It is DAZ content, so it stays out of the repository: `TempAssets/` is in `.gitignore`.
The game loads `../../TempAssets/CharBlend.fbx`, or the file given by `-character path`, scales it
from its joint bounds to the Derp's size, puts it in the Derp's place and moves the Derp aside.
Without the file, or when the import fails, the Derp stands in and the reason is printed.

- Assimp cannot read the supplied `CharBlend.fbx`: "FBX-Parser (TOK_DATA, offset 0x226d2da) failed
  to parse ID, unexpected data type, expected L(ong) (binary)". The same `.blend` exported by
  Blender 5.2 or 4.3 imports in 2.2 s, with default settings, with leaf bones, with baked animation
  and with embedded textures, so the supplied file was written some other way.
- The file has no clips, so the gate ran on a scratch export of the `.blend` with two actions added
  by a Blender script ("Raise": both upper arms; "Bow": spine and neck). The game builds "Wave" and
  "Sway" in code for a Genesis 9 skeleton whose file has fewer than two clips. Both sets key
  rotations only, by joint name, so they survive changes to the character's proportions.

**Gate.** Both backends, Debug, validation clean, with the scratch export:

- `-animation-test`: "Animation test: bind pose identity for 144 joints" and "Skinning test: 256
  vertices matched on 4202 frames, largest error 4.57764e-05" on Vulkan, 4032 frames on D3D12. The
  144 joints are the bones and the armature; no import warnings, so the seven meshes agree on every
  inverse bind. The character's units are centimetres, hence the larger error.
- The two clips come from the file; the character plays one and cross-fades to the other, and
  `-crowd 100` cross-fades its copies ("Crowd: 21 copies, 142 cross-fades started" on both).
- Without the character the Derp passes as before: 4 joints, 108 vertices, largest error 1.9e-06.

Earlier, before the character, the Derp alone ran with two clips built in code ("Dance" and "Sway"),
both at the bind pose at time 0, so `-freeze-animation` shows the rest pose.

Each read-back vertex in the skinning check is also checked to lie inside the culling sphere of its
frame.

**RHI** (step 1, "Phase 2 corrections")

- `BufferState::VertexBuffer` and `IndexBuffer`, a base vertex on `DrawIndexed`, `CopyBuffer`, and
  `Readback::RequestBuffer`.
- Skinning and its check are the first clients of `ReadWriteStorageBuffer`, `TransitionBuffers` and
  `CopyBuffer`, and all three work on both backends. `CopyBufferToImage` still has no client.

**Engine**

- One matrix convention: row vectors, `Model[j] = Local[j] * Model[parent]`,
  `Skin[j] = InverseBind[j] * Model[j]`. Every Assimp matrix is transposed on import, bone offsets
  included (finding 7).
- `Engine/Animation`: `Skeleton`, `Clip` (linear keys, rotations by normalised lerp on the shorter
  arc), `Pose` (`Blend`, `BuildPalette`), `AnimatorComponent` (named states, fades requested by code,
  an automatic next state when a clip that does not loop ends) and `AnimationSystem`, which
  `GameRunFrame` updates before extraction. `-freeze-animation` holds every animator at time 0.
- Import: `AI_CONFIG_IMPORT_FBX_PRESERVE_PIVOTS` is off. The skeleton is every bone node and its
  ancestors below the model root. Skinned vertices are baked into model space with joint indices,
  so one palette serves the whole character (finding 9). Inverse binds come from the bone offsets
  moved into model space, with a warning when meshes disagree. Joints are not scene nodes; a mesh
  without skinning under a joint is attached to the model root with a warning. Each joint stores the
  largest distance to a vertex it moves. Clips are read one per `aiAnimation`.
- Assets: `ResourceType::Skeleton` and `ResourceType::AnimationClip`, written as `.asset` files
  beside the meshes. `MeshAsset` lost both bone arrays (finding 8) and gained a skeleton field.
- `DerpMover` and `MeshComponent::BonePalette` are gone. A mesh component finds the animator on
  its nearest ancestor once, and owns its own skinned copies, so copies of a character share the
  mesh asset. `SceneNode` now deletes its components, which leaked before.
- The Derp's skeleton is 4 joints: the armature (scale 100) and three bones.

**Renderer**

- Buffers in the pass graph: `ImportBuffer`, `SetBuffer`, `ReleaseBuffer`, and `BufferWrites` and
  `BufferReads` on `PassDesc`. Writers run before readers and every buffer is undefined at the
  start of a frame. The D3D12 debug layer accepts that, so no state is kept across frames.
- `Renderer/Skinning`: one pool buffer of static `Vertex` layout, at most
  `Skinning::MaxPoolVertices` (9,586,980 vertices, 512 MB: D3D12 buffer views hold 2^27 words), ranges claimed by `Enlist` and
  returned by `Retire`, a larger pool and new descriptor sets when it is full. One compute pass
  (`Order` just after mip generation) dispatches once per skinned object. Vertices are read and
  written as 32-bit words, with `static_assert`s on the 56- and 88-byte layouts. Positions use the
  full skin matrix; normal, tangent and bitangent its 3 x 3, normalised (finding 11). A vertex with
  no weights keeps its bind position.
- `RenderObject` gained `SkinnedMesh` and a world-space `Bounds`. A skinned object draws alone from
  the pool with its base vertex, its own index buffer and the static pipeline. Its bounds are the
  joints grown by their radii (finding 10).
- Deleted: `vs_pbr_skinned.hlsl`, `vs_vsm_skinned.hlsl`, `SkinMatrix` and the `Bones` binding,
  `InstanceData::BoneOffset` (instances are 128 bytes), the per-layout pipeline arrays and the
  layout bits of the batch key.
- `Readback::WatchBuffer` and `RequestBuffer` for graph buffers, ordered like watched images.
- An "Animation" panel (characters, joints, skinned vertices, animation CPU ms, skinning GPU ms),
  and an `Animation:` line with the same figures on exit.

**Checked**

- Debug: Standalone Vulkan and D3D12, Editor `-play` on both, `-stress`, `-compute-test`,
  `-animation-test` and `-crowd 100` on both. Every run exits 0 and stderr holds only "DirectX
  debugging enabled." and the Noesis message. The compute test still passes.
- Rest pose: on Vulkan the frozen frames of steps 3 and 4 differ only where the new panel is; the
  Derp's cells are unchanged. Steps 2 and 3 differ only in the cells that change between run
  states. Vulkan against D3D12 gives a mean of 3.7 to 4.0 in the same cells as the Phase 2 runs in
  different run states; no pair of runs in this phase landed in the same state, so the 0.23 figure
  was not reproduced.
- Release `-crowd 100 -novsync` with the character: the pool holds 21 copies of its 427,610
  vertices, so the crowd is cut to 21 and says so. 23 characters, 3,172 joints, 9,407,528 skinned
  vertices: Vulkan 2.3 ms a frame, animation 0.10 ms CPU, skinning 0.90 ms GPU; D3D12 3.9 ms,
  0.11 ms and 2.5 ms. With the Derp alone (101 characters, 10,908 vertices) Vulkan was 0.28 ms and
  D3D12 0.34 ms. Release `-animation-test` passes on both.
- Debug `-crowd 100` with the character: Vulkan 11 ms, D3D12 22 ms.
- Debug `-stress` is unchanged: Vulkan 32 ms, D3D12 54 ms, which includes GPU-based validation
  (finding 5).

Open items:

- The supplied `CharBlend.fbx` did not import. It is kept as `CharBlend.original.fbx` and replaced
  by a Blender 5.2 export (no leaf bones, no baked animation), which the game loads by default; with
  no clips in it, the character plays the clips built in code.
- The pool caps a crowd of this character at 21. More needs a smaller mesh (the body is subdivided
  to 402,600 vertices), several pools, or skinning only what a view can see.
- The character draws with the Derp's material for every submesh until Phase 4.
- Morph targets: no asset has them. The skinning shader would apply them before the bones.
- Skinned normals use the 3 x 3 of the skin matrix, exact for rotation and uniform scale only.
- Every character is animated and skinned whether or not a view sees it.
- Attaching objects to joints needs a later feature; joints are not scene nodes.
- Animator states live only at runtime; only the skeleton field of `AnimatorComponent` is saved.
- Skeletons, clips and mesh assets made by the import are never freed, as `MeshAsset` was before.

Carried, not part of Phase 3:

- Every launch re-imports the FBX files and rewrites their `.asset` files and `registry.bin`.
  Cooked assets are the fix.
- The open and carried items under "Phase 2 outcome".

## Verdict

EngineDev is a viable starting point: keep it. The slow, unglamorous parts already work on both backends, and most of what the cache system needs is additive.

This is from reading the main branch at commit 0240868 (12 May 2026). It does not yet cover the NewArchitectureRough branch, which holds 19 later commits up to 30 August 2026: a Dear ImGui editor, an asset and serialization system, scene nodes and a start on per-material draw bins. The project is Windows-only, so I did not build or run it.

- **What carries over.** About 11,000 lines of RHI with Vulkan 1.3 and Direct3D 12 at parity, one HLSL source compiled for both, deferred PBR, variance shadow maps, GPU skinning, resize handling, input and a UI layer.
- **What is missing.** Compute, GPU-written textures, storage buffers on Vulkan, readback, and any per-frame structure. These are exactly what the cache system leans on.
- **What must be restructured, not added.** Two things. The frame is a fixed list of pipelines that own their attachments, and draws are registered once at load. Both block batching and the cache passes.
- **True of main only.** The UI layer is NoesisGUI and draw batching has not started. Both moved forward on NewArchitectureRough, so parts of this assessment and of phases 0 and 1 will change once that branch is read.

## What exists today

The RHI is real and symmetric across both backends; everything above it is placeholder.

| Area | State | Notes |
| --- | --- | --- |
| Backends | Working | Vulkan 1.3 with dynamic rendering, and Direct3D 12, chosen at startup by a setting. Windows only |
| Shaders | Working | One HLSL source compiled by DXC to DXIL and SPIR-V, through a hand-run batch file with a fixed list |
| Pipelines | Working | Described as data. Variants share a parent's targets, and a pipeline can take earlier pipelines' outputs as inputs. Hull and domain stages are wired but untested |
| Frame | Fixed | Shadow, G-buffer, lighting, then UI, in creation order. Each pipeline owns its attachments, and barriers are hard-coded around that |
| Draws | Retained | Registered once at load into per-variant bins. No removal, culling, sorting, instancing or batching |
| Resources | Partial | Buffers and images behind integer IDs. Images must be uploaded from CPU data, with 1 mip and 1 layer. Buffers are never freed at runtime, and each resource is its own device allocation |
| Descriptors | Partial | Sets per pipeline and slot. Dynamic uniform buffers work on both backends. Storage buffers and storage images are never written on the Vulkan side |
| Lighting | Working | Deferred PBR with 4 lights and variance shadow maps rendered with multiview |
| Skinning | Working | Since Phase 3: a skeleton imported from the node tree, clips, an animator with fades, and compute skinning once per frame into a pool drawn with the static pipelines. Clip import from a file is untested |
| Import | Working | Assimp for FBX, stb_image for textures. A material is one of two hard-coded texture layouts, found by file name |
| UI | Working | NoesisGUI on both backends, with Noesis-specific calls inside the RHI executor |
| Engine side | Placeholder | TempGameObject, a static active camera, and an input command system. About 1,600 lines |
| Build and repo | Fragile | Visual Studio solution only. One absolute user path in the Engine project. The Noesis SDK is 5,585 of the repo's 5,829 files (528 MB). Compiled shaders are committed. No README or tests |

Defects found while reading, all small and worth fixing first:

1. `Uploader::GetBufferAllocation` returns a reference to a temporary, so every caller reads a dangling reference.
2. Each draw's push constants are a raw pointer into `TempGameObject::ModelDataArray`, which reserves 100 entries. An object with more meshes reallocates the vector and leaves earlier draws pointing at freed memory.
3. The Vulkan `DrawIndexed` pushes constants with the vertex stage hard-coded, ignoring the stages the pipeline declared.
4. `GetDescriptorSet` and `GetBufferAllocation` return by value, so the draw loop copies a vector for every set bound on every draw.
5. A dynamic buffer has one mapped copy shared by every frame in flight, so the CPU can overwrite data a queued frame still reads.
6. `SceneNode` returns its children and meshes by value, so walking a model copies each subtree.
7. `CoreInitData::SwapchainMSAASamples` is declared `bool`.
8. `InputState.cpp` exists twice, in RHI and Engine, with identical contents.

## Gaps against the cache system

Every pass in the [cache design](https://claude.ai/artifact/KGxq9yzHtA7DHYSkKvGDLZ) depends on a renderer feature that does not exist yet. Each one is general-purpose, so none needs to be written as cache-specific code.

| Need | Used by | Today | Work |
| --- | --- | --- | --- |
| Compute pipelines and dispatch | Feature pass, page bake, later skinning | Only enum bits exist | New pipeline type on both backends, plus compute passes in the frame |
| Images created empty and writable from compute | Texel page atlas | Images require CPU data; no storage path | Extend image creation; add 16-bit and integer formats |
| Storage buffers in any stage | Page table, vector lists, bone palettes | Layout type exists; Vulkan never writes it | Finish on Vulkan, verify on Direct3D 12 |
| GPU to CPU readback | Feedback buffer | None | Copy to a mapped buffer, read a few frames later |
| Ordered, dependent passes | Bake coarse levels before fine, before shading | Fixed pipeline list | Pass graph |
| Per-frame draw lists | Culling, batching, subdivision | Retained bins | Rebuild each frame from the scene |
| Per-frame constant data | UV anchors, bone palettes, bake lists | One shared mapped buffer | Ring allocator per frame in flight |
| Material as a shader interface | Material shader | Two hard-coded texture layouts | Surface interface; procedural skin is one implementation |
| Flexible vertex formats | Fixed-point UVs, a second UV set | Two hard-coded structs | Vertex layout stored per mesh |
| Sampler objects | Atlas needs clamp and point filtering | Two global samplers | Sampler descriptions |
| GPU timing | Checking the budgets | None | Timestamp queries shown in the overlay |
| Tessellation or mesh shaders | Optional subdivision | Stages wired, untested | Test the path, choose a method |
| Skeleton and clips | The character | Hand-animated bones | See skinning and animation |

One existing cost works against the VRAM goal. The G-buffer stores world position and normals in 32-bit float targets, which is 162 MB with depth at 2560 × 1440. That is more than the 88 MB planned for the whole texel cache. Rebuilding position from depth and packing normals into two channels brings it to about 59 MB.

## Phase detail

Each phase adds general renderer capability and ends at a gate that must hold on both backends. Sizes are relative judgments, with the two-backend bring-up you already did counting as large.

**Phase 0. Stabilize and restructure (small).**

- Split the RHI library into three layers. RHI: device, resources, pipelines, command recording. Renderer: passes, materials, mesh and texture assets. Engine: scene, animation, logic. Mesh, Material, GeometryImport and Renderer leave the RHI.
- Replace the Noesis calls in the executor with one generic external-pass hook. Noesis and Dear ImGui both attach through it.
- Add Dear ImGui as the debug overlay. Every later phase reports through it.
- Use typed, generation-checked handles in place of raw integers and void pointers, with a deferred-free queue keyed by frame. Fix the defects listed above.
- Repo: move the Noesis SDK out of the tree, remove the absolute path, make shader compilation a build step, add a README with build steps.
- Gate: the same image as today, validation layers clean, frame time on screen.

**Phase 1. Frame structure (large).** This is the unfinished batching work, done at the level where it holds.

- A minimal scene of entities with a transform, mesh and material, which the renderer reads each frame. TempGameObject goes away.
- Per-frame draw lists: cull, build a sort key from pipeline, material and mesh, and merge equal neighbours into instanced draws.
- Object data moves from push constants to a per-frame storage buffer indexed per instance. This needs storage buffers finished on Vulkan.
- A ring allocator per frame in flight for all per-frame constants.
- A pass graph. Passes declare what they read and write; the graph orders them, owns transient attachments, derives barriers and handles resize. Pipelines stop owning attachments.
- Slim the G-buffer while the attachments are being moved.
- Gate: 10,000 objects batched, and a new pass needs no edits to core code.

**Phase 2. Compute and GPU data (medium).**

- Compute pipelines and dispatch, with compute passes in the graph.
- Images created empty, with mips, array layers, storage access, sub-rectangle copies and more formats.
- Sampler objects, delayed readback, GPU timestamp queries.
- First client: mip generation for loaded textures, which have no mips today.
- Gate: a compute pass writes a texture, a raster pass samples it, and the CPU reads it back two frames later.

**Phase 3. Skeleton and animation (medium).** Covered in the next section.

**Phase 4. Materials and paging (large).**

- Materials become data: a shader, a parameter block and bindings. Each implements one surface interface that fills the G-buffer inputs. Today's textured PBR is the first implementation.
- A generic paged-texture service: page table, atlas, feedback pass with readback, least-recently-used eviction and a per-frame fill budget. Page producers plug in.
- First producer: file-backed pages. It proves the service with no procedural code involved.
- Gate: a large texture streams in page by page as the camera approaches, inside a fixed atlas.

**Phase 5. Procedural skin on the character (large).**

- Second producer: the feature pass and page bake from the cache design.
- The procedural surface material: page lookup, capped live bands, normal from slope, albedo from the pigment lookup.
- The band table as a hot-reloaded asset, with overlay views for page residency, level hit and bake cost.
- A static test mesh first, then the skinned character.
- Gate: zoom from full body to pores at fixed VRAM and fixed fragment cost.

**Phase 6. Subdivision and deep zoom (medium, optional).**

- Tessellation or mesh shaders, with displacement read from the page atlas.
- Fixed-point UV anchors and camera-relative transforms.
- Gate: a displaced silhouette, and stable UVs when the view covers less than 1/500 of a chart.

## Skinning and animation

The importer needs a real skeleton before any clip can play, and skinning should move from the vertex shader to one compute pass per frame.

**What exists.**

- An 88-byte skinned vertex with 4 weights, and inverse bind matrices imported per mesh.
- A 128-matrix uniform buffer per object, filled by DerpMover for three bones by hand.
- The joint hierarchy and clips are never read from the file. `BoneTransforms` is sized but never filled.
- Every pass re-skins: four shadow views plus the G-buffer. A comment in the skinned shader marks its normal transform as doubtful.

**Plan (phase 3).**

1. Import a skeleton from the Assimp node tree: joints with a parent index, local bind transform, inverse bind matrix and name. Import clips as translation, rotation and scale tracks per joint.
2. Evaluate poses at runtime: sample clips, blend, walk parents to model space, multiply by the inverse bind. The result is one matrix palette per character per frame.
3. Write palettes to the per-frame storage buffer, with an offset per instance. The 128-bone limit goes away.
4. Add a compute skinning pass that writes skinned position, normal and tangent to a vertex buffer per instance. Every later pass draws that buffer with the static vertex layout, so the skinned pipeline variants are deleted.
5. Apply morph targets in the same pass, before the bones, if the character's face needs them.
6. Add an animator component in the engine layer: clip playback, cross-fades and a small state machine.

Compute skinning costs one extra vertex buffer per skinned instance, about 4 MB per 100,000 vertices. In return the character is skinned once per frame instead of five times, materials never multiply into skinned variants, and subdivision can read skinned positions before the vertex stage.

**Where it meets the cache.**

- Pages are keyed by chart UV, so deformation never invalidates them.
- The mesh needs one UV set with no overlaps. Mirrored UVs are split or given a second set at import.
- Band wavelengths are world units measured at bind pose, so the importer stores a UV-to-world scale per chart.
- Stretch under animation changes the pixel footprint, which the material shader already measures. Page requests therefore follow the deformed surface.
- Pose-driven detail, such as expression wrinkles, is a band whose amplitude comes from a joint angle or morph weight. It stays live, or invalidates only its own pages.
- Displacement, if used, pushes along the skinned normal from the compute pass.

## Toward an engine

Game code talks to a scene, and the renderer reads a snapshot of it. Nothing outside the renderer submits draws.

- **Scene.** Entities with a transform hierarchy and components: mesh, skinned mesh, light, camera, animator. This replaces TempGameObject, DerpMover and the static active camera.
- **Extraction.** Once per frame the renderer copies what it needs from the scene. This boundary is what later allows a render thread.
- **Loop.** A fixed timestep for logic and a variable one for rendering. The existing input command system carries over.
- **Logic.** Native C++ systems first, behind a narrow API. A scripting language is a later decision.
- **Assets.** Cooked formats and handles, so Assimp and stb_image leave the runtime. Hot reload for shaders and band tables.
- **UI.** Noesis for game UI and Dear ImGui for tools, both through the external-pass hook.
- **Later.** Physics, audio, scene files and an editor.

## Risks and open questions

- **Two backends.** Every RHI feature in phases 1, 2 and 6 is built twice. I suggest leading with Vulkan, the current default, and reaching parity at each gate. Dropping Direct3D 12 would shorten those phases; that is your call.
- **Not built here.** The assessment is from reading. Validation-layer state and real frame cost are unknown until it runs.
- **Noesis licence.** The SDK's LICENSE.txt restricts distributing its source, and the full SDK, including Src, is in the public repo. It is worth reading before the next push.
- **Pass graph scope.** It is easy to over-build. The target is ordering, transient attachments and barriers, with no automatic pass merging or async compute.
- **Character asset.** Phase 5 needs a humanoid with clean, non-overlapping UVs and at least two clips. Which character do you intend to use?
- **Carried over from the cache design.** Page table form, chart seams and the subdivision method are still open there.
